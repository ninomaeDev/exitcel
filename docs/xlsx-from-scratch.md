# ライブラリを使わずに .xlsx を読み書きした話

Exitcel は外部ライブラリを一つも使っていません。`package.json` すらありません。
その制約でいちばん重いのが **`.xlsx` の読み書き**でした。ここをどう通したかを書きます。

対象コード: [`js/xlsxio.js`](../js/xlsxio.js)（978行）

---

## 最初に — どこまでが自前か

先に線を引いておきます。「全部自分で書いた」と言うと嘘になるので。

| 部分 | 誰が書いたか |
|---|---|
| ZIP のコンテナ構造（ヘッダ・目次・終端レコード） | **自前** |
| CRC32 | **自前** |
| xlsx の XML 生成と解析 | **自前** |
| 圧縮・展開（deflate 本体） | **ブラウザ標準の `CompressionStream` / `DecompressionStream`** |

つまり **「圧縮アルゴリズムは書いていないが、ZIP というファイル形式は自分で組み立てた」** が正確なところです。
deflate を自分で実装するのは目的ではなかったので、ブラウザが標準で持っているものを使いました。

---

## .xlsx の正体

拡張子を `.zip` に変えると展開できます。中身はこうです。

```
book.xlsx
├─ [Content_Types].xml          この ZIP に何が入っているかの申告
├─ _rels/.rels                  入口。「本体は xl/workbook.xml」と示す
├─ docProps/core.xml            作成者・更新日時
├─ docProps/app.xml             アプリ名
└─ xl/
   ├─ workbook.xml              シートの一覧
   ├─ _rels/workbook.xml.rels   シート名 -> 実ファイルの対応
   ├─ styles.xml                フォント・色・罫線・表示形式
   ├─ worksheets/sheet1.xml     セルの値と数式
   ├─ drawings/drawing1.xml     図形・グラフ・画像の配置
   └─ media/image1.png          画像の実体
```

**ZIP を書ければ、あとは XML を組み立てるだけ**です。逆に言えば、ZIP が書けないと一歩も進めません。

---

## ZIP を書く

ZIP は「順番に並べるだけ」の素直な形式です。3種類の塊でできています。

```
[ローカルヘッダ + 中身] [ローカルヘッダ + 中身] ... [目次] [終端レコード]
 ^ファイル1              ^ファイル2                 ^全ファイル分  ^目次の位置を持つ
```

書き出しは 30 バイトのヘッダを組み立てるところから始まります。

```js
var lh = new Uint8Array(30 + nameU8.length);
var dv = new DataView(lh.buffer);
dv.setUint32(0, 0x04034b50, true);  // 署名 "PK\3\4"
dv.setUint16(6, 0x0800, true);      // ファイル名は UTF-8 だと宣言する
dv.setUint16(8, method, true);      // 0=無圧縮 / 8=deflate
dv.setUint32(14, crc, true);        // 展開後データの CRC32
dv.setUint32(18, body.length, true);// 圧縮後サイズ
dv.setUint32(22, raw.length, true); // 展開後サイズ
```

`true` はリトルエンディアン指定です。ZIP は全フィールドがリトルエンディアンなので、ここを間違えると
「壊れた ZIP」としか言われず、原因にたどり着くのに時間がかかります。

最後に **終端レコード（EOCD）** を 22 バイト置いて終わりです。ここに目次の位置とファイル数が入っていて、
読む側はまずこれを探します。

---

## ZIP を読む — 末尾から探す理由

読み込みは先頭からではなく **末尾から** 始めます。

```js
for (var i = u8.length - 22; i >= Math.max(0, u8.length - 66000); i--) {
  if (dv.getUint32(i, true) === 0x06054b50) { eocd = i; break; }
}
```

EOCD は末尾にありますが、**末尾ちょうどとは限りません**。ZIP は最大 65535 バイトのコメントを
末尾に付けられる仕様だからです。そのため「末尾から 65535 + 22 バイトの範囲を後ろ向きに走査して
署名を探す」のが正しい読み方になります。`66000` という半端な数字はここから来ています。

### ハマったところ：ローカルヘッダを読み直す

目次（セントラルディレクトリ）には、各ファイルの位置・サイズ・名前が全部載っています。
なので目次だけ読めば済みそうに見えますが、**データの開始位置だけは目次から計算できません**。

```js
var lho = dv.getUint32(p + 42, true);      // 目次が持つ「ローカルヘッダの位置」
var lnLen = dv.getUint16(lho + 26, true);  // ローカルヘッダ側の名前長を読み直す
var leLen = dv.getUint16(lho + 28, true);  // ローカルヘッダ側の拡張領域長を読み直す
var dataStart = lho + 30 + lnLen + leLen;
```

理由は、**拡張フィールド（extra field）の長さが目次側とローカルヘッダ側で一致しないことがある**ためです。
仕様上どちらも自由に付けられるので、目次の値でデータ位置を計算すると、ツールによっては数バイトずれます。
ここは目次を信じず、必ずローカルヘッダから読み直す必要があります。

## CRC32

ZIP は各ファイルの CRC32 を持ちます。合わないと展開時に弾かれます。

```js
var CRC_TABLE = (function () {
  var t = new Uint32Array(256);
  for (var n = 0; n < 256; n++) {
    var c = n;
    for (var k = 0; k < 8; k++) c = (c & 1) ? (0xEDB88320 ^ (c >>> 1)) : (c >>> 1);
    t[n] = c >>> 0;
  }
  return t;
})();
```

多項式 `0xEDB88320` は標準的な CRC-32 のビット反転表現です。256 個の表を起動時に一度作り、
以降は 1 バイトずつ表引きします。`>>> 0` を挟んでいるのは、JavaScript のビット演算が
符号付き 32 ビットで返るためです。これを忘れると負の値になり、`setUint32` に渡した時点で壊れます。

## 効いた小さな判断

派手さはないものの、入れておいてよかったものです。

**1. 圧縮して小さくならなければ、圧縮しない**

```js
if (comp && comp.length < raw.length) { method = 8; body = comp; }
```

短い XML は deflate を通すと逆に大きくなります。その場合は無圧縮（method 0）で格納します。

**2. 画像は最初から圧縮しない**

```js
files.push({ name: 'xl/media/' + m.name, data: m.data, store: true });
```

PNG や JPEG はすでに圧縮済みです。もう一度 deflate にかけても縮まらず、時間だけ消費します。

**3. タイムスタンプを固定する**

```js
dv.setUint16(10, 0, true);       // 時刻 0
dv.setUint16(12, 0x2821, true);  // 日付 2000-01-01
```

現在時刻を書くと、**同じ内容から作った xlsx のバイト列が実行するたびに変わります**。
固定にしておけば、出力が同一かどうかをファイルの比較だけで判定できます。

**4. `CompressionStream` が無ければ無圧縮で出す**

```js
async function deflateRaw(u8) {
  if (typeof CompressionStream === 'undefined') return null;
  ...
  } catch (e) { return null; }
}
```

`null` が返れば呼び出し側は method 0 にフォールバックします。ファイルは大きくなりますが、
**Excel では問題なく開けます**。動かないより大きいほうがましだ、という判断です。

**5. ファイル名は UTF-8 だと宣言する**

汎用フラグの `0x0800` を立てています。これを忘れると、日本語を含むファイル名が
展開ソフトによって文字化けします。

## テストで担保していること

この入出力は QA のテストケースで固定しています（[`qa/`](../qa/) 参照）。

- 書き出した xlsx を **自分で読み込み直して**、値と数式・書式・複数シートとシート名・結合セル・日付が
  日付のまま保たれるかを5件で確認（TC-U-034〜038）
- テストケース一覧の xlsx 自体を、**Exitcel の xlsx エクスポータで生成**している（ドッグフーディング）

「書けるが読めない」「読めるが Excel で開けない」を防ぐには、往復で確認するのがいちばん確実でした。

## やってみて

ZIP は、仕様書を読めば素直に組み立てられる形式でした。詰まったのは形式そのものではなく、
**仕様に「こう書いてもよい」と書かれている自由度**のほうです。拡張フィールドの長さが
両側で違いうること、末尾コメントのせいで EOCD の位置が固定でないこと。どちらも
「普通は起きないが、起きたら読めない」たぐいのもので、実ファイルを何本か通して初めて気づきました。

ライブラリを使えば 3 行で済む処理です。それでも一度自分で通しておくと、
`.xlsx` が壊れたときに「どこを見ればいいか」が分かるようになりました。
